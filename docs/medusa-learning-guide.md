# Medusa 小白学习手册

> 面向刚接触 Medusa、但已经了解域名、HTTPS 和服务器基础概念的项目所有者。本文先解释系统和术语，不要求先会编程或运维。
>
> Medusa 是持续发展的软件。本手册用于建立概念；具体安装命令、环境变量和行为，应以项目实际使用的 Medusa 版本及其官方文档为准。

## 1. Medusa 是什么？

Medusa 是一套可自行托管和扩展的**电商后端系统**。它负责电商业务和数据，并通过 API（应用程序接口）让店面、管理后台及其他服务与它交互。

它不是自动生成完美店面的一键建站工具。通常需要把 Medusa 后端与一个顾客店面搭配起来；本项目的目标是 Medusa + Next.js Storefront。

```text
顾客浏览器
    │ 浏览商品、购物车、结账
    ▼
Next.js Storefront（顾客看到的店面）
    │ 通过 Store API 请求电商数据和操作
    ▼
Medusa 后端 ───── Medusa Admin（商家管理界面）
    │                       │ 商家管理商品、订单等
    ├── PostgreSQL：长期业务数据
    ├── Redis：队列等运行状态
    └── 对象存储：商品图片等文件
```

这里的“前后端分离”表示店面和业务后端是**两个可以独立开发、构建、部署的应用**，通过 API 协作。它们不是互不相关：店面需要知道后端地址和公开 API key，后端也需要允许正确的店面来源访问。

## 2. Storefront、后端、Admin、API 的区别

| 名称 | 是什么 | 谁使用 / 做什么 |
|---|---|---|
| **Storefront** | 顾客店面，本项目计划使用 Next.js | 顾客浏览商品、操作购物车、结账；页面设计和交互主要由前端代码决定 |
| **Medusa 后端** | 运行业务规则和提供 API 的 Node.js 应用 | 读取和写入电商数据，执行商品、购物车、订单、支付等业务逻辑 |
| **Medusa Admin** | 管理 Medusa 数据的网页后台，随 Medusa 应用提供 | 商家登录后维护商品、价格、库存、订单等；不等同于顾客店面 |
| **Store API** | 面向店面和顾客流程的接口 | 店面读取可售数据、创建购物车等；请求通常需要 Publishable API Key |
| **Admin API** | 面向管理操作的接口 | Admin 用于有权限的管理操作；不能把管理密钥放进浏览器或顾客店面 |

可以把 Medusa 想成店铺的“业务中枢”：店面负责呈现和收集顾客操作，Medusa 负责理解这些操作并处理业务数据。

## 3. 改商品和改程序有什么区别？

这是判断是否要重新部署时最有用的区别：**数据变更通常不等于代码变更**。

| 需求 | 通常改什么 | 通常是否要重新部署应用 |
|---|---|---|
| 在 Admin 上传商品、修改商品描述或价格 | Medusa 数据库里的商品数据 | 不需要 |
| 在 Admin 处理订单或维护库存 | Medusa 业务数据 | 不需要 |
| 更换首页布局、商品卡片样式或页面交互 | Next.js Storefront 代码 | 通常只部署 Storefront |
| 增加 Admin 当前不支持的字段、接口或业务规则 | Medusa 后端代码/配置 | 通常要部署后端 |
| 安装或调整支付、邮件、配送集成 | 后端模块/配置，以及可能的前端交互 | 视集成范围部署相关应用 |
| 升级 Medusa 或修改数据模型 | 后端依赖/代码和数据库 schema | 部署后端，通常还要执行迁移 |

因此，商品录入和日常运营通常不需要开发者发布代码；但后端并不是永远不用更新。安全修复、Medusa 升级、新的业务能力或配置变化仍可能需要后端发布。

> “通常”很重要：有些环境变量在构建时会被写入前端产物，有些在运行时读取。改配置是否只需重启或还要重建，应看具体配置和框架要求。

## 4. Medusa 模块与工作流是什么？

### 模块（Module）

模块是按业务领域组织的功能单元，例如 Product（商品）、Cart（购物车）、Order（订单）、Payment（支付）、Inventory（库存）和 Fulfillment（履约）。可以把它理解成电商业务系统里的不同部门。Medusa 也允许开发者按需要添加自定义模块或集成。

### 工作流（Workflow）

工作流把多个业务步骤组织成一个有顺序的流程。例如结账可能要检查购物车、计算金额、创建支付并完成订单相关步骤。工作流帮助把复杂业务拆成可协调的步骤。

刚开始使用时不需要立刻编写模块或工作流。先通过 Admin 和现有店面了解平台已有能力；只有当现有功能或集成不满足需求时，再判断是否要扩展后端。

## 5. PostgreSQL、Redis、对象存储分别存什么？

- **PostgreSQL**：主要业务数据库，保存商品、订单、顾客等需要长期保存的数据。要备份，并验证恢复过程。
- **Redis**：Medusa 生产环境会使用它支持队列、事件和后台任务等运行能力。它不是 PostgreSQL 的替代品；具体用途与配置应按所用 Medusa 版本确认。
- **对象存储**：保存商品图片等文件。生产中通常使用 S3 兼容服务；若文件只放在应用容器的临时文件系统里，换容器或机器时可能丢失或无法访问。

数据库备份和图片存储是两件事：数据库里通常保存图片引用/元数据，图片文件本身可能在对象存储中。设计备份时应分别考虑。

## 6. Docker：镜像和容器

- **Docker 镜像（image）**：应用代码和运行环境的打包产物，可以类比为“应用安装包”。
- **容器（container）**：镜像启动后运行起来的实例，可以类比为“正在工作的程序”。
- **Docker Compose**：用配置文件描述多个容器及其网络、数据卷、依赖关系，然后作为一套服务管理。

Medusa 官方提供 Docker 安装/本地运行指导，也提供 Medusa 应用的生产构建流程。它们不等于一个已经包含你未来所有自定义代码、密钥和业务配置的通用生产商店镜像。项目有自己的代码和依赖，通常需要构建**属于这个项目版本**的镜像。

PostgreSQL 数据要放在持久化卷或外部数据库中，不要把“容器能重建”误解为“数据也能随意删除”。应用容器可以替换，业务数据必须有独立保存和备份方案。

## 7. CI、GitHub Actions、GHCR 是什么？

- **CI（持续集成）**：代码更新后自动进行检查、测试和构建，帮助尽早发现问题。
- **GitHub Actions**：GitHub 提供的自动化执行平台，可在代码提交或合并时运行 CI，也可执行部署任务。
- **GHCR（GitHub Container Registry）**：GitHub 的容器镜像仓库，用于存放已构建的 Docker 镜像。
- **CD（持续交付/部署）**：把通过检查的产物交付到服务器，或者自动更新服务器的流程。

常见发布链路：

```text
开发者把代码提交到 GitHub
        ↓
GitHub Actions 安装依赖、检查、测试、构建镜像
        ↓
镜像推送到 GHCR，并使用版本号/commit 标记
        ↓
VPS 拉取指定版本镜像并启动容器
        ↓
检查健康状态和关键业务，再决定是否继续发布
```

GitHub Actions 可以构建 Medusa 后端镜像和 Next.js 店面镜像。CI 不仅能构建，也能配置自动部署；初期可先做到“检查 + 构建 + 上传镜像”，由人手动在 VPS 发布，确认过程可靠后再自动化。

密钥（数据库密码、支付 Secret Key、JWT 密钥、对象存储 Secret 等）不能提交到 Git，也不应烘焙进镜像。应通过 GitHub Secrets、部署平台的密钥配置或服务器上的受保护环境文件提供。

## 8. 本项目的目标自托管结构

目前选定的方向是**自行管理 VPS**，初期将 PostgreSQL 和 Redis 与应用放在 VPS 上，通过 Docker Compose 管理服务。目标结构如下；它是计划，不代表已经实现或验证：

```text
VPS
├── 反向代理 / TLS 入口（按部署方案配置）
├── Next.js Storefront 容器
├── Medusa Server 容器：Store API + Admin API + 管理界面
├── Medusa Worker 容器：后台任务、订阅器、定时任务
├── PostgreSQL 容器：持久业务数据 + 备份
└── Redis 容器：队列等运行服务

外部服务
├── S3 兼容对象存储：商品图片（目标方向：Cloudflare R2）
├── GHCR：保存 CI 构建的镜像
└── 支付、邮件等业务集成（实施时逐项确定）
```

Medusa 官方生产部署指南建议把应用分为 **server mode** 和 **worker mode** 两个运行实例：Server 面向 API/Admin 请求，Worker 处理后台任务。它们可以运行同一版本的项目构建，但以不同模式启动。Worker 不需要对顾客公网开放。开始实施时要根据所选 Medusa 版本验证确切配置和启动命令。

### 发布应用不等于迁移业务数据

一般发布会更新应用镜像，但不能随意重建或清空数据库卷。升级 Medusa 或数据模型时，部署流程还要执行适用的数据库迁移；迁移可能改变 schema，回退应用镜像不一定能自动撤销迁移。因此要先备份、测试升级，并预先设计回滚方式。

### 自托管的维护责任

把数据库和 Redis 放在同一台 VPS，前期月成本可能较低，但机器或磁盘故障会同时影响应用和数据库。至少需要：

1. 将 PostgreSQL 备份复制到 VPS 之外的安全位置；
2. 定期演练从备份恢复，而不只是确认备份文件存在；
3. 为商品图片等对象存储资产考虑独立的访问和备份策略；
4. 监控磁盘、内存、服务健康与后台队列；
5. 为测试环境使用隔离的数据库、Redis、密钥，避免误操作正式数据。

## 9. Staging、迁移与回滚的基本概念

- **开发环境**：开发者写代码和本地验证的环境。
- **Staging（预发布/测试环境）**：在正式发布前验证候选版本，使用独立数据和测试密钥；不要连接真实支付或正式数据库。
- **Production（生产环境）**：顾客真实访问和下单的正式店铺。
- **数据库迁移（migration）**：升级数据库结构或相关数据的版本化步骤。涉及数据的迁移需要备份，并先在 staging 验证。
- **回滚（rollback）**：新版本出问题时恢复到可用版本。应用镜像可保留旧版本便于切回，但若数据库迁移不兼容旧代码，不能只切换镜像就认为回滚完成。

发布前至少应确认：目标镜像版本、迁移步骤、备份完成、健康检查方式、失败时的恢复步骤。

## 10. 后续学习顺序

用户计划在部署后亲自进入 Medusa Admin 实际操作，因此可以按下面的顺序边看边学：

1. **认识 Admin**：登录后台，区分商品、变体、价格、库存、区域、订单等概念。
2. **自己建一个测试商品**：观察哪些信息是商品数据，哪些内容由 Storefront 的页面代码控制。
3. **让店面展示商品**：理解 Storefront 如何通过 Medusa Store API 读取商品；Publishable API Key 与 Admin Secret Key 不同。
4. **走一遍测试购物车/下单**：看购物车、支付和订单状态如何关联；仅用测试支付配置，不接收真实付款。
5. **判断何时需要开发**：先确认需求能否通过 Admin 配置完成；无法配置时，再定位是前端展示问题、Medusa 后端业务问题，还是第三方服务集成问题。
6. **再学习扩展**：按需阅读 Medusa 的模块、工作流、API Route、Subscriber 和 Provider 文档，不必一开始全部掌握。
7. **上线前验证**：测试支付成功/失败、重复和延迟 webhook、订单通知、退款、库存/履约，以及备份恢复和发布回滚。
